\CNsection{1}{Why Diameter Was Introduced}

\CNchained\CNsubsection{}{RADIUS Limitations}

RADIUS (Remote Authentication Dial-In User Service) was designed in the 1990s for dial-up access. As networks evolved toward 3G/\allowbreak{}4G, RADIUS could not meet modern requirements:

{\def\LTcaptype{none} % do not increment counter
\Needspace{16\baselineskip}
\begin{longtable}[c]{@{}
  >{\raggedright\arraybackslash\hspace{0pt}}m{(\linewidth - 2\tabcolsep) * \real{0.5789}}
  >{\raggedright\arraybackslash\hspace{0pt}}m{(\linewidth - 2\tabcolsep) * \real{0.4211}}@{}}
\toprule\noalign{}
\rowcolor{CNink}\CNth{Limitation} & \CNth{Impact} \\
\CNheadrulesep
\endhead
\bottomrule\noalign{}
\endlastfoot
\textbf{UDP transport (unreliable)} & Messages can be lost silently; no built-in retransmission \\
\textbf{No server-initiated messages} & Server cannot push policy changes or disconnect users proactively \\
\textbf{Limited AVP space} & 8-bit attribute type field = max 255 attribute types \\
\textbf{No application-layer ACK} & Cannot confirm message delivery at application level \\
\textbf{Weak security model} & Shared secret + MD5 only; no hop-by-hop TLS built-in \\
\textbf{No capability negotiation} & Peers cannot discover supported features \\
\textbf{Client-server only} & No peer-to-peer; no agent/\allowbreak{}relay architecture \\
\end{longtable}
}

\CNsubsection{}{Diameter’s Answer}

Diameter (the name implies ``twice the RADIUS'') was defined in \textbf{RFC 6733} to address all these limitations:

\begin{itemize}
\tightlist
\item
  Reliable transport (TCP/\allowbreak{}SCTP)
\item
  Server-initiated messages (push model)
\item
  32-bit AVP code space (4+ billion attribute types)
\item
  Built-in capability exchange and error handling
\item
  Agent architecture for scalable routing
\item
  Native TLS/\allowbreak{}DTLS support
\end{itemize}

\begin{CNquote}

\CNwarn{} \textbf{Key Concept}: Diameter is a \textbf{CONTROL PLANE} protocol only. It carries signaling (authentication, authorization, accounting, policy) — never user data traffic.

\end{CNquote}

\CNsubsection{3.2}{Peer Connections}

\begin{itemize}
\tightlist
\item
  \textbf{Transport}: TCP (default) or SCTP (preferred for multi-homing)
\item
  \textbf{Port}: 3868 (plaintext) or 5868 (TLS)
\item
  \textbf{Persistent}: Connection stays up; monitored by watchdog (DWR/\allowbreak{}DWA)
\item
  \textbf{Peer-to-peer}: Both endpoints can initiate messages
\item
  \textbf{Capability Exchange}: CER/\allowbreak{}CEA must succeed before application messages
\end{itemize}

\CNsubsection{3.3}{Realm-Based Routing}

Diameter routes messages based on \textbf{realms} (domain-like identifiers):

\begin{itemize}
\tightlist
\item
  Each node is configured with a realm (e.g., \CNcode{epc.}\allowbreak{}\CNcode{mnc001.}\allowbreak{}\CNcode{mcc208.}\allowbreak{}\CNcode{3gppnetwork.}\allowbreak{}\CNcode{org})
\item
  Routing table maps realms \ensuremath{\to} peer connections
\item
  Agents use \CNcode{Destination-Realm} AVP to determine next hop
\item
  Enables multi-operator and roaming scenarios
\end{itemize}

\CNsection{5}{Diameter Commands}

\CNchained\CNsubsection{5.1}{Naming Convention}

All Diameter commands follow the pattern:

\begin{itemize}
\tightlist
\item
  \textbf{Request}: \CNcode{X-Request} (abbreviated \CNcode{XR}) — R flag = 1
\item
  \textbf{Answer}: \CNcode{X-Answer} (abbreviated \CNcode{XA}) — R flag = 0
\end{itemize}

Every request MUST receive exactly one answer.

\CNsubsection{7.2}{AIR (Authentication-Information-Request) Details}

\textbf{Purpose}: MME requests fresh authentication vectors from HSS

\textbf{Key AVPs in AIR}:\CNbr{}\textbar{} AVP \textbar{} Purpose \textbar{}\CNbr{}\textbar{}—–\textbar{}———\textbar{}\CNbr{}\textbar{} User-Name \textbar{} IMSI of the subscriber \textbar{}\CNbr{}\textbar{} Visited-PLMN-Id \textbar{} 3-byte MCC+MNC of visited network \textbar{}\CNbr{}\textbar{} Requested-EUTRAN-Authentication-Info \textbar{} Specifies how many vectors needed \textbar{}\CNbr{}\textbar{} Number-Of-Requested-Vectors \textbar{} Typically 1-5 \textbar{}\CNbr{}\textbar{} Re-Synchronization-Info \textbar{} Sent if previous auth failed (SQN sync) \textbar{}

\CNsubsection{7.3}{AIA (Authentication-Information-Answer) Details}

\textbf{Purpose}: HSS returns E-UTRAN authentication vectors

\textbf{Key AVPs in AIA}:\CNbr{}\textbar{} AVP \textbar{} Purpose \textbar{}\CNbr{}\textbar{}—–\textbar{}———\textbar{}\CNbr{}\textbar{} Result-Code \textbar{} 2001=success, 5001=user unknown \textbar{}\CNbr{}\textbar{} Authentication-Info (Grouped) \textbar{} Contains the vectors \textbar{}\CNbr{}\textbar{} E-UTRAN-Vector (Grouped) \textbar{} One complete auth vector \textbar{}\CNbr{}\textbar{} ├─ RAND \textbar{} 128-bit random challenge \textbar{}\CNbr{}\textbar{} ├─ XRES \textbar{} Expected Response (for verification) \textbar{}\CNbr{}\textbar{} ├─ AUTN \textbar{} Authentication Token (for mutual auth) \textbar{}\CNbr{}\textbar{} └─ \ensuremath{K_{\mathrm{ASME}}} \textbar{} Key for NAS/\allowbreak{}AS security derivation \textbar{}

\CNsubsection{7.4}{ULR (Update-Location-Request) Details}

\textbf{Purpose}: MME registers itself as serving MME for this subscriber

\textbf{Key AVPs in ULR}:\CNbr{}\textbar{} AVP \textbar{} Purpose \textbar{}\CNbr{}\textbar{}—–\textbar{}———\textbar{}\CNbr{}\textbar{} User-Name \textbar{} IMSI \textbar{}\CNbr{}\textbar{} Visited-PLMN-Id \textbar{} Serving network identity \textbar{}\CNbr{}\textbar{} RAT-Type \textbar{} E-UTRAN (LTE) \textbar{}\CNbr{}\textbar{} ULR-Flags \textbar{} Indicates initial attach vs TAU \textbar{}

\CNsubsection{7.5}{ULA (Update-Location-Answer) Details}

\textbf{Purpose}: HSS acknowledges and returns complete subscription profile

\textbf{Key AVPs in ULA}:\CNbr{}\textbar{} AVP \textbar{} Purpose \textbar{}\CNbr{}\textbar{}—–\textbar{}———\textbar{}\CNbr{}\textbar{} Result-Code \textbar{} Success or failure \textbar{}\CNbr{}\textbar{} Subscription-Data (Grouped) \textbar{} Complete subscriber profile \textbar{}\CNbr{}\textbar{} ├─ MSISDN \textbar{} Phone number \textbar{}\CNbr{}\textbar{} ├─ AMBR \textbar{} Aggregate Max Bit Rate (UL + DL) \textbar{}\CNbr{}\textbar{} ├─ APN-Configuration-Profile \textbar{} All configured APNs \textbar{}\CNbr{}\textbar{} └─ Subscriber-Status \textbar{} SERVICE\_\allowbreak{}GRANTED or BARRED \textbar{}

\CNsubsection{8.2}{Why 5G Moved Away from Diameter}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Simpler tooling}: HTTP/\allowbreak{}2 + JSON leverages existing web infrastructure (proxies, load balancers, API gateways)
\item
  \textbf{Web-native}: Standard REST APIs — easier for developers, standard debugging tools
\item
  \textbf{Stateless design}: Enables cloud-native microservices, horizontal scaling, Kubernetes orchestration
\item
  \textbf{Cloud-friendly}: No persistent peer connections; standard load balancing works
\item
  \textbf{Flexibility}: JSON schema evolution is easier than binary AVP definitions
\item
  \textbf{Ecosystem}: Massive HTTP/\allowbreak{}2 ecosystem (libraries, tools, monitoring)
\end{enumerate}

\CNsubsection{8.4}{Migration: 4G/\allowbreak{}5G Interworking}

Diameter is NOT gone — it persists at interworking boundaries:

\begin{itemize}
\tightlist
\item
  \textbf{Diameter Routing Agent (DRA)} still used in 4G
\item
  \textbf{Interworking Function (IWF)} translates Diameter \ensuremath{\leftrightarrow} HTTP/\allowbreak{}2 at 4G/\allowbreak{}5G border
\item
  NSA (Non-Standalone) 5G still uses EPC with Diameter
\item
  Full migration to SA (Standalone) 5G eliminates Diameter within the core
\end{itemize}
